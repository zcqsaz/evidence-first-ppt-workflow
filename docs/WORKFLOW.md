# Evidence-First PPT Workflow：详细执行规范

## 1. 规范目的

本规范定义一套可复用、可审计、可自动验收的学术PPT生产流程。它把PPT制作拆成相互制约的九个阶段，并为每个阶段规定：

- 输入；
- 必须执行的动作；
- 强制产物；
- 质量门禁；
- 失败后的返工入口；
- 可自动检查的字段。

最终目标不是“生成PPTX文件”，而是交付一个事实可靠、视觉可读、公式正确、来源可追溯、版本一致的学术演示系统。

## 2. 规范性术语

本文使用以下术语：

- **必须 / MUST**：不满足即不得进入下一阶段；
- **禁止 / MUST NOT**：发现即判定为缺陷；
- **应该 / SHOULD**：默认执行，只有记录理由后才可偏离；
- **可以 / MAY**：按项目需要选择；
- **证据资产**：用于支撑页面论点的论文图、官方图、地图、数据产品、实景照片、公式或表格；
- **出版商原始单图**：由期刊或出版商单独提供的完整图片文件，而非论文页面截图；
- **严格资产**：进入正式PPT且需要执行来源、完整性、哈希和裁剪检查的图片或公式文件；
- **内容池**：原始文档中可供筛选的事实、定义、公式和解释，不等于最终页面正文；
- **页面规格**：构建PPT前对单页任务、结论、证据、内容和验收条件的冻结描述；
- **版式构图**：同一视觉模板内的阅读路径和信息组织方式，不等于另一套母版；
- **交付否决项**：任一项失败都不得交付的硬性门禁。

## 3. 角色与责任

小型项目可由同一人承担多个角色，但责任不能省略。

| 角色 | 主要责任 | 不得独自批准的内容 |
|---|---|---|
| 项目负责人 | 冻结目标、范围、受众和交付标准 | 自己新增的重大范围变化 |
| 内容负责人 | 提取事实、设计叙事、编写页面规格 | 未核验外部事实 |
| 证据审计者 | 检索真实图、登记元数据、核对图题 | 自己无法确认归属的素材 |
| 视觉实现者 | 模板映射、排版、PPTX构建 | 删除强制内容以适配版面 |
| QA审查者 | 结构检查、渲染检查、引用检查 | 未记录的例外 |
| 最终批准人 | 确认可放映、可交付、版本一致 | 含否决项的文件 |

AI可承担检索、提取、编排、编码和初步审计，但来源归属、版权条件、科学解释和最终交付仍需责任人确认。

### 4.1 文件保护

- `00_input/original/` 中的文件必须保持只读语义，不覆盖、不改名；
- 用户修改后的PPT优先级高于旧构建脚本产物；
- 每次任务开始必须在 `PROJECT.md` 冻结允许修改的文件清单；
- 中间文件不得写入正式交付目录；
- 受限输入和未授权素材不得提交到公开仓库。

## 5. 阶段0：项目启动与范围冻结

### 5.1 输入

- 用户需求；
- 目标PPT或模板；
- Word、Markdown、PDF、图片和补充资料；
- 交付时间与放映场景。

### 5.2 必须执行

1. 识别项目类型：课程、项目申报、答辩、汇报、论文分享或其他；
2. 记录目标受众、时长、目标页数、语言、页面比例；
3. 写明允许拆页、合并、删除和补充外部资料的边界；
4. 冻结允许修改的具体文件；
5. 记录模板、字体、配色、页码和引用要求；
6. 记录禁用措辞、禁用素材和禁止的制作方式；
7. 指定阶段批准人。

### 5.3 强制产物

- `PROJECT.md`；
- `project_config.json`；
- `STATUS.md`；
- `CHANGELOG.md` 初始记录。

### 5.4 通过门禁

- 修改范围无歧义；
- 模板来源和主文件明确；
- 是否允许联网检索、是否允许自绘图、是否需要可编辑PPTX已明确；
- 原始文件已登记且不会被构建脚本直接覆盖。

### 5.5 失败与返工

若用户同时提供多个相似PPT但未指定主文件，先通过文件时间、目录和用户修改痕迹调查；仍无法确定且选择会改变结果时，停止构建并请求确认。

## 6. 阶段1：输入提取与证据映射

### 6.1 目标

把Word、Markdown、PPT、PDF和图片转化为可检索的事实、结构和来源映射，避免在排版阶段才发现内容缺失。

### 6.2 必须执行

1. 为每个输入分配稳定 `source_id`；
2. 提取标题、章节、正文、表格、公式、图片和引用；
3. 渲染参考PPT并分析用户修改过的页面；
4. 区分：可进入PPT的学术内容、仅供制作的内部说明、需要外部核验的事实；
5. 为关键论断建立 `claim_id → source_id → 原文位置` 映射；
6. 标记矛盾、缺失、时效性和版权风险。

### 6.3 强制产物

- `source_manifest.md`；
- `source_summary.md`；
- `evidence_map.csv`；
- 参考PPT渲染图或模板分析输入。

### 6.4 通过门禁

- 关键事实可追溯；
- 内部制作标签不会进入PPT；
- 已识别需要外部图或补充文献的页面；
- 用户修改页已被视为新的视觉事实来源，而不是被旧脚本忽略。

## 7. 阶段2：叙事与教学/汇报结构

### 7.1 目标

先确定观众如何理解，再确定页面数量。不得从模板页反推内容结构。

### 7.2 课程PPT需要回答

- 学生进入本节前知道什么；
- 学完后应形成什么认知转变；
- 核心概念、方法、误区和证据链是什么；
- 哪些内容需要观察、比较、推导、诊断或迁移；
- 与前后章节怎样衔接。

### 7.3 项目汇报需要回答

- 为什么立项；
- 现有工作还缺什么；
- 本项目做什么、怎样做、难点是什么；
- 创新是否由方法与证据支撑；
- 计划、目标和基础是否形成闭环。

### 7.4 强制产物

- 至少两条候选叙事；
- 候选比较与风险；
- `approved_storyline.md`；
- 章节—页数—时间预算。

### 7.5 通过门禁

- 只有一条批准的主线进入页面设计；
- 每一部分的必要性能够解释；
- 目录不使用“模块几”等内部制作语言；
- 章节顺序与用户要求一致。

## 8. 阶段3：逐页规格

### 8.1 页面不是知识点容器

每页必须先定义：

1. `page_function`：本页在叙事中的功能；
2. `reasoning_task`：建立、区分、排除、验证或迁移什么；
3. `audience_action`：观众要观察、比较、推导或判断什么；
4. `page_conclusion`：本页可以成立的最小结论；
5. `visual_evidence`：支撑结论的图、数据、公式、表格或文本证据；
6. `content_points`：至少4条实质知识点；
7. `limitations`：适用条件、误差来源或解释边界；
8. `citations`：页内引用；
9. `acceptance`：可观察的通过条件。

### 8.2 页面类型最低契约

| 页面类型 | 最低内容契约 |
|---|---|
| 封面 | 题目、章节/项目、单位/作者、日期；模板正确 |
| 目录 | 单列章节、当前部分高亮；不写制作标签 |
| 图文证据页 | 结论、完整图、中文图题、3—4条解释、边界、来源 |
| 公式页 | 结论、正确公式、参数解释、适用条件、误差、来源 |
| 表格页 | 明确比较维度、至少3—4行实质内容、结论、来源 |
| 文字页 | 两组互补信息，每组约4条，避免空泛短语 |
| 方法路线页 | 输入、处理、输出、质量控制、验证和风险 |
| 总结页 | 回收已证明的结论，不引入未经铺垫的新事实 |

### 8.3 通过门禁

- 每页只有一个主要视觉中心；
- 结论能由本页证据支撑；
- 内容不是项目语言与课程语言的混合；
- 相邻页具有新的认知增量；
- 所需素材已明确，不能写“随便找一张相关图”。

## 9. 阶段4：真实素材检索与审计

详细规则见 [standards/REAL_ASSETS.md](standards/REAL_ASSETS.md) 与 [standards/PUBLISHER_ACCESS.md](standards/PUBLISHER_ACCESS.md)。

### 9.1 必须执行

1. 先锁定项目/方法正式名称、核心论文、官方页面和产品文档；
2. 优先下载出版商原始单图、官方原图或矢量文件；
3. 逐图核验归属、变量、时间、区域、单位、产品性质和图号；
4. 对期刊来源建立论文级 `access_log.csv`，记录DOI、出版社、访问路由、访问依据、版本、许可证/条款和失败状态；
5. 建立一图一记录的 `source_metadata.csv`；
6. 生成素材总览，人工查看是否完整；
7. 建立交付脚本素材白名单；
8. 失败时记录搜索词、页面、错误和替代方案。

### 9.2 通过门禁

- 不使用搜索引擎缩略图、无来源转载、AI生成科研图或不相干装饰图；
- 出版商原图存在时不使用PDF截图；
- 图中无正文碎片、残缺图注、页眉页脚；
- 原图质量满足最终放映尺寸；
- 无法核验的图不进入正式PPT。
- 订阅、OA、作者仓储或许可等访问依据已记录；不得绕过出版社访问控制或公开再分发受限二进制文件。

## 10. 阶段5：视觉系统与模板映射

### 10.1 模板先审计，后填内容

模板分析必须记录：

- 页面比例；
- 顶部母版带、校徽、箭头和禁入区；
- 标题安全区；
- 正文有效区；
- 页脚安全区；
- 页码几何中心；
- 需要统一遮罩或删除的母版元素；
- 字体、字号、配色与线条规则。

### 10.2 版式构图

同一PPT只使用一套视觉模板，但准备2—3种信息构图，例如：

- 图左文右；
- 图右文左；
- 全宽图 + 下方解释；
- 公式 + 图/参数解释；
- 原生学术表格；
- 双栏高密度文字；
- 地图 + 验证图；
- 技术路线 + 关键说明。

“三种排版”不等于三套母版。连续两页不得只替换文案而保持相同阅读路径。

### 10.3 代表页门禁

批量构建前，至少完成并渲染：

- 一页图文页；
- 一页公式页；
- 一页表格页；
- 一页高密度文字页；
- 一页最长标题页；
- 一页目录或章节导航页。

代表页必须检查标题高度、图幅完整性、正文密度、页码、页脚和字体。

## 11. 阶段6：可重复构建

### 11.1 构建原则

- 正式PPT必须能由脚本或明确的可重复步骤重新生成；
- 构建脚本不得自动回退到未经审计的临时素材；
- 用户修改后的现有PPT作为输入时，应在其基础上修改，而不是从旧版本重建；
- 先输出到中间目录，重新打开成功后再复制到正式路径；
- 每次生成记录输入哈希、脚本版本、输出哈希和时间。

### 11.2 图片

- 科研图使用等比 `fit`；
- PowerPoint裁剪值必须为0；
- 不拉伸、不压扁；
- 多面板图在最终尺寸不可读时必须换图或独立成页；
- 默认一图只用一次。

### 11.3 公式

- 保存LaTeX源代码；
- 渲染为透明高分辨率PNG或SVG；
- 检查括号、分式、上下标、求和范围和向量粗体；
- 公式页同时解释参数、条件和误差；
- 普通正文不得残留 `a_1`、`z_i` 等源码碎片。

### 11.4 表格

- 使用原生可编辑表格；
- 不把表格截图放进装饰框；
- 表头、行高、换行和对齐必须在渲染后检查；
- 只有关系真正需要行列比较时才使用表格。

### 11.5 文字

- 默认使用项目指定字体；
- 信息密度不能依靠极小字号；
- 禁止“阅读要点、课堂解读、图示所支持、课程示意、模块几”等制作语言；
- 标题不得进入母版禁入区；
- 页脚与几何居中的页码上下分离。

## 12. 阶段7：质量保证

详细规则见 [standards/QA_ACCEPTANCE.md](standards/QA_ACCEPTANCE.md)。

### 12.1 自动结构检查

至少检查：

- PPTX可重新打开；
- 页数与规格一致；
- 对象越界；
- 文本框几何重叠；
- 项目符号实际溢出；
- 图片裁剪；
- 媒体重复哈希；
- 字体；
- 禁用措辞；
- 页码位置；
- 严格素材哈希能否映射到审计目录。

### 12.2 实际渲染

- 必须使用PowerPoint或目标放映环境渲染全部页面；
- 推荐输出1600×900 PNG；
- 生成缩略图总览；
- 所有含图页、公式页、表格页、目录页和最后三页必须原尺寸检查；
- 最终轮必须全量渲染，不能只渲染修改页。

### 12.3 五至八轮复核

推荐顺序：

1. 来源与事实；
2. 图片完整性与匹配；
3. 公式与表格；
4. 文字重叠、换行和标题边界；
5. 信息密度与版式同质化；
6. 页码、页脚、母版和字体；
7. 重复媒体、对象越界和版本；
8. 最终放映与证据地址回查。

每轮必须写明发现、修改和复查结果。仅写“已检查”不合格。

### 12.4 交付否决项

- 任一科研图不完整；
- 任一复杂公式排版错误；
- 任一正文页信息密度不合格；
- 任一关键事实无法追溯；
- 正式文件与交付副本版本不一致；
- 目标放映环境无法正常打开或渲染。

## 13. 阶段8：交付与归档

### 13.1 交付物

- `final.pptx`；
- 需要时提供 `final.pdf`；
- `handoff.md`；
- `delivery_validation.md`；
- `source_metadata.csv`；
- `checksums.sha256`；
- 已知限制与不可公开素材说明。

### 13.2 版本一致性

1. 保存正式PPT；
2. 使用PPT库重新打开；
3. 使用目标PowerPoint全量渲染；
4. 复制到交付目录；
5. 比较正式文件与交付副本SHA-256；
6. 在交付报告中记录哈希。

### 13.3 公开发布前

- 删除真实项目输入、内部报告和个人信息；
- 不提交无权再分发的论文图、模板、字体或商标；
- 可保留脱敏元数据、搜索方法和空白示例；
- 检查仓库中不存在本机绝对路径、账号、密钥和内部网址。

## 14. 例外管理

任何偏离强制规则的情况都必须写入 `delivery_validation.md`，至少包括：

- 例外规则；
- 发生原因；
- 风险；
- 替代控制；
- 批准人；
- 是否影响公开发布。

不得用“时间有限”“先这样”作为未记录的例外。

## 15. 完成定义

项目只有同时满足以下条件才算完成：

- 事实、图片和公式可追溯；
- 页面规格与最终页一致；
- 指定模板、字体和几何规则被执行；
- 图片完整、无裁剪、无拉伸；
- 页面信息密度和排版多样性通过；
- 自动QA无未批准错误；
- 全量渲染人工复核通过；
- 正式文件与交付副本哈希一致；
- 交付说明和已知限制完整。
